# ADR-0002 — Distribute NapkinStack on PyPI

- **Status**: Accepted (2026-09-15, after the v0.1.0 release); clarified 2026-09-20 (two channels, one published artefact)
- **Date**: 2026-09-15
- **Decision makers**: NapkinStack maintainers (`@NapkinStack/maintainers`)
- **Scope**: project (the engine)
- **Reversibility**: costly — a published name and a learned command change badly

---

## Context

PDR-0001 (Proposed) makes uv the only prerequisite and requires a project's workstation and
CI to run the NapkinStack version it pins (R3). ADR-0001 (Proposed) makes the repository's
tags, in PEP 440 format, the skeleton's versions; the engine and the skeleton therefore
share the same version (R2).

The GitHub organisation only allows actions published by GitHub, pinned by SHA. The
repository contains no secret and must not contain one.

## Problem

Under what name, through which registry and through which publication circuit is
NapkinStack distributed?

## Constraints

- Installable by `uv tool install`, with no other prerequisite.
- The package version identical to the repository's tag.
- No publication secret stored.
- A package name and a command name with no collision.

---

## Prior art

**Dominant convention of the field:** for a Python command-line tool, PyPI, an isolated
install (`uv tool install`, `pipx`), publication from CI through Trusted Publishing (an
ephemeral OpenID Connect token, no stored secret).

**References examined:**

| Reference | What it does | Applicable here? |
|---|---|---|
| GitHub Spec Kit | A Python CLI installed by `uv tool install`, updated the same way | Yes: the install |
| uv (official publishing guide) | `uv_build`, the version in `pyproject.toml` (`uv version --bump`), a workflow on tag, two separate jobs, a `pypi` environment, Trusted Publishing | Yes: build and circuit |
| PyPI / PyPA (`pypa/gh-action-pypi-publish` v1.14.2) | Publication through Trusted Publishing, provenance attestations (PEP 740) generated by default | Yes: the publication step |
| An npm package, a Go or Rust binary | Other registries and formats | No: the tooling is Python (PDR-0001) |

---

## Options considered

### Option 1 — PyPI, `napkinstack`, the `nstack` command, the uv + PyPA circuit
- Description: the `napkinstack` distribution; the `nstack` command; an `uv_build` build;
  publication on tag through Trusted Publishing with `pypa/gh-action-pypi-publish`.
- Advantages: each brick's own convention; attestations with no extra tool; no secret.
- Drawbacks: two third-party actions to authorise by name in the organisation.
- Exit cost: renaming means a new package and a new command for every project.

### Option 2 — The same distribution, published by `uv publish` and `astral-sh/attest-action`
- Advantages: a single tool for build and publication.
- Drawbacks: the attestation action is young (v0.0.6, 10 stars); it fails the niche filter
  (`skeleton/docs/os/06-decisions.md` §3).

### Option 3 — The same distribution, uv installed by `pip`, no third-party action
- Advantages: the organisation's action policy stays unchanged.
- Drawbacks: departs from uv's official path (`astral-sh/setup-uv`), which R3 will make
  necessary anyway to run the pinned version in CI.

### Option 4 — Do nothing
- No distribution: `init` and `update` are impossible, PDR-0001 cannot exist.

---

## Decision

**Option 1.**

| Element | Choice | Verified fact |
|---|---|---|
| Registry | PyPI | — |
| Distribution name | `napkinstack` | Free on PyPI (2026-09-15) |
| Command | `nstack` | The PyPI package `nstack` (0.2.1, 2018) installs no command; nor does the npm package `nstack` (0.0.1) |
| Install | `uv tool install napkinstack` | Spec Kit's convention |
| Build | `uv_build`, the version written in `pyproject.toml`, bumped by `uv version --bump` | `uv_build` refuses dynamic metadata (uv 0.12.14, `crates/uv-build-backend/src/metadata.rs`) |
| Published version | Tag `vX.Y.Z` equal to the project's version; publication refused otherwise | PEP 440 tags required by Copier (ADR-0001) |
| Circuit | A workflow on a version tag: a build job with no permission, a publish job as the only one to receive `id-token: write`, a `pypi` environment | uv's official guide |
| Publication | `pypa/gh-action-pypi-publish`, Trusted Publishing, attestations by default | The action's README |
| uv in CI | `astral-sh/setup-uv` | uv's official path |

The two third-party actions are added **by name** to the organisation's allow list, pinned
by SHA like the others. They are the only exceptions to the "GitHub actions only" rule.

No placeholder publication: the first published version is a real version, at the end of
the implementation plan. PyPI discourages name squatting (PEP 541).

### Deviation from the convention

None.

---

## Success criterion

*(Convention adopted: criterion not mandatory.)* The first published version installs
through `uv tool install napkinstack` on a fresh workstation, shows its provenance
attestation on PyPI, and its publication used no stored secret.

**Observed on 2026-09-15**, on v0.1.0:

- `uv tool install napkinstack==0.1.0 --with-executables-from pre-commit`, with isolated
  tool directories and cache: `nstack 0.1.0` and `pre-commit` installed; `nstack init`
  creates a project from the published tag, which passes its fitness functions, its hooks
  and `nstack new-module`;
- PyPI's integrity API: one attestation for the wheel and one for the source archive, a
  GitHub trusted publisher, repository `NapkinStack/engineering-os`, workflow
  `release.yml`, environment `pypi`;
- no secret: `release.yml` references none, the PyPA action receives no password and
  exchanges the job's OpenID Connect token.

---

## Consequences

**Positive:**

- No PyPI token to store or renew.
- Every published version is tied to its workflow and its commit by an attestation.
- A single version number for the engine, the skeleton and the package.

**Negative and accepted debt:**

- The organisation's action policy widens to two named actions.
- A PyPI account under the NapkinStack identity, with mandatory 2FA, carries the trusted
  publisher; managing it stays a human action.
- The name `nstack` remains an unreserved command name: another tool could install it one
  day.

**Impacts on other modules or contracts:** `platform/` becomes an installable Python
package; D18 (`make` and `pip` absent) is solved by uv.

**Rule to automate:** publication fails when the tag differs from the project's version.
The publication workflow is covered by the existing hooks: zizmor (permissions, pinning,
the `use-trusted-publishing` audit) and actionlint.
`skeleton/docs/os/07-governance.md` §2

---

## Rejected alternatives

- **`uv publish` with `astral-sh/attest-action`**: the attestation action is too young.
- **uv installed by `pip`**: a departure from the official path to avoid an authorisation
  that R3 will require anyway.
- **The `napkin` command**: a binary already installed by the npm package `napkin-ai`,
  which also uses a `.napkin/` folder.
- **The `os.py` or `manage.py` command**: shadows the standard `os` module, or collides
  with a Django module.
- **The `napkinstack` command**: no collision, but long to type every time; it stays the
  distribution name.

## Clarification of 2026-09-20 — two channels, one published artefact

Added while deciding how the framework is adopted (PDR-0006's neighbour question), without
changing the decision.

**Observation.** This ADR chose a registry and never said whether the repository is also a
way in. Since [PDR-0005](../pdr/0005-work-on-the-framework-while-using-it.md) a project may
already be pinned to a ref and its CI installs from the forge — but a newcomer has no
documented gesture other than the registry, while the field's default in this niche is the
forge: [Spec Kit](https://github.com/github/spec-kit/blob/main/docs/installation.md)
documents "two official channels", its repository and PyPI, and shows the git route first,
pinned to a release tag. `uv` installs either without a line of code from us.

**Clarification.** There are two channels and one artefact of reference.

- **The registry publishes.** PyPI carries the artefact of a `vX.Y.Z` tag, with its
  provenance attestation. That artefact, and only it, is *published*: it is what a project
  records, what CI installs for a published pin, and what the checklist and the release
  method talk about. Nothing here changes.
- **The forge distributes the same tag's source.** `uvx --from git+<repository>@vX.Y.Z` and
  `uv tool install` of the same are supported, documented gestures — to try the tool without
  installing it, and to install it where the registry is awkward.
- **A git install is never published.** A tag can be moved and carries no attestation, so
  the tool keeps saying where its own code came from: it names the ref it was asked for, and
  refuses to call it published. That is PDR-0005's rule applied to the tool itself.

**Two consequences, both measured on 2026-09-20 against the published v0.4.0.**

- A project created through the forge channel **at a tag** is identical to one created from
  the registry: Copier records `_commit: v0.4.0` and the repository as `_src_path`, so the
  project's own CI resolves the registry. The channel a project was born through leaves no
  trace in what judges it, which is why the forge channel needs no mechanism of its own.
- A **mutable ref** — a branch, `HEAD` — is never a documented gesture for a user. It is the
  contributor's loop (PDR-0005), where every run announces the unpublished framework and the
  diagnosis reports it. pre-commit draws the same line for its own hook repositories: a
  branch in `rev:` "is not supported".

**What this does not change:** the release method, the tag, Trusted Publishing, the
attestations, or the definition of a published version. A project still moves between
published versions on demand (PDR-0001), and the registry stays the only channel that
publishes.
