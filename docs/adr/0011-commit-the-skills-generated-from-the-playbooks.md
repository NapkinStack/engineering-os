# ADR-0011 — Commit the skills generated from the playbooks

- **Status**: Accepted (2026-11-20, by the decider: *go D252*); built in D252
- **Date**: 2026-11-20
- **Decision makers**: NapkinStack maintainers (`@NapkinStack/maintainers`)
- **Scope**: project — the skeleton's `.gitignore` and `.gitattributes`, the engine (`init`,
  `update`, `skills`, `pr-scope`), the handbook
- **Reversibility**: easy — the two folders put back in `.gitignore` and removed from the index

---

## Context

`nstack skills` generates one `SKILL.md` per playbook into `.claude/skills/` (Claude Code) and
`.agents/skills/` (Codex and the tools that read the open layout, D245). Since the skills were
first generated they were **git-ignored**: derived files, never committed, the playbooks being the
single source. On a person's workstation that holds: they ran `nstack skills`.

## Problem

An agent that starts from a fresh clone — a cloud agent (Copilot's coding agent, Codex in the
cloud, Claude Code on the web), a new contributor's — finds no skill, unless it thinks of running
`nstack skills`. Those are the agents the method is for. And S3 never applied in CI: there was
nothing there to compare.

## Constraints

- One source of truth: the playbooks (`06-decisions.md` §9); a skill is never edited.
- No step of an agent's own: whatever it is, a fresh clone must be enough.
- No new red for a project at the version that brings it: the update itself must leave the project
  whole.

## Prior art

The tools nearest the method write their agents' files into the repository and refresh them with a
command of their own: Spec Kit (`specify init`, its upgrade path) writes `.claude/skills/`,
`.agents/skills/` and `.github/prompts/`; OpenSpec (`openspec init`, `openspec update`) writes
`.claude/skills/openspec-*/SKILL.md` and `.github/prompts/`. Claude Code shares a project's skills
through git. Copilot loads the skills a repository holds. Generated-but-committed is the lockfile's
pattern: the source is elsewhere, the output is versioned, CI says when they drift.

## Options considered

1. **Keep them ignored**, and generate in each agent's setup.
2. **Commit them**, regenerated by `init` and `update`, checked by S3 in CI.
3. **Symbolic links** from one tool's folder to the other's, committed.

Option 2, on the decider's word.

## Decision

1. **Committed.** The skeleton's `.gitignore` no longer names the two folders. `nstack init`
   generates the skills before the initial commit; `nstack update` regenerates them before its own
   commit — a project that never committed them gets them in that pull request.
2. **Still derived.** `.nstack/playbooks/` stays the source of truth (`06-decisions.md` §9). A
   skill is never edited: S3, now run in CI on the committed files, fails one that drifted from its
   playbook or was edited by hand.
3. **Folded in review.** `.gitattributes` marks both folders `linguist-generated`; the review budget
   (P2) leaves them out, as it leaves out lockfiles.
4. **Said where git ignores them.** `nstack skills` warns where a `.gitignore` from before still
   leaves a folder out.

## Rule to automate

S3, already built: in CI, on the committed files, a skill that differs from what its playbook
generates fails.

## Deviation

None from the method: a source of truth and its derived output, as with a lockfile. It reverses
only the earlier choice to keep the output out of git.

## Consequences

- **A new gate after adoption.** Once a project has committed its skills, a pull request that changes
  a playbook without running `nstack skills`, or edits a skill by hand, fails S3 in CI. That is the
  intent; the update that brings this version is green.
- **The engine shapes the bytes.** What a skill holds depends on the engine that generated it: a
  contributor whose engine is not the project's version may generate other bytes, which S3 in CI
  says. The pre-push hook already refuses an engine behind the project's.
- **A person's own skills in those folders** are folded in review and left out of the review
  budget too: the attributes and the budget read the folder, not who wrote the file.

## Rejected alternatives

- **Generate in each agent's setup** (`copilot-setup-steps.yml`, a cloud agent's script): one
  setting per tool, each forgotten in turn.
- **Symbolic links** from one folder to the other: Windows checks them out as text.
- **`.github/skills/` as a third folder**: not before it is known whether Copilot also reads
  `.agents/skills/`.

## Success criterion

> We will consider this was the right call if, before **2027-03-31**, an agent starting from a
> fresh clone of a project loads its skills with no step of its own, and no pull request of that
> project is held up by a skill that drifted, beyond the commit that regenerates it.
